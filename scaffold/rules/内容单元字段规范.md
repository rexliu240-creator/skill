# 内容单元字段规范

## 文件规则

- 每个内容单元必须是独立 Markdown 文件，放在 `02-内容单元库/`
- 文件名固定为 `ID_标题.md`，例如 `OPI003_内容要复用不是要收藏.md`
- 文件开头必须有 YAML frontmatter；正文引用其他单元时统一写 `[[文件名]]`
- 当前文件代表当前有效版本，历史变化交给 Git，不建 `_v2` 文件

## 最小字段

| 字段 | 必填 | 说明 |
|---|---|---|
| id | ✅ | 单元唯一编号：类型前缀 + 三位序号（如 QST001） |
| type | ✅ | QST / CON / OPI / CAS / SOL，五选一 |
| title | ✅ | 单元标题，一句话，陈述内容本身 |
| canonical | ✅ | true=当前有效版本；false=被合并/已废弃 |
| version | ✅ | 正整数，字段或正文实质修改时 +1 |
| created | ✅ | 创建日期 YYYY-MM-DD |
| source_documents | ✅ | 来源文档相对路径列表，至少 1 条，保证可追溯 |
| themes | ✅ | 所属主题列表，至少 1 条，供主题地图聚合 |
| keywords | ✅ | 关键词列表，供去重与检索 |
| relationships | ✅ | 关系列表，允许为空列表，但字段本身必须存在 |

## 类型判定口径

- **QST**：值得单独回答的问题。一个单元一个问题。
- **CON**：有稳定定义、会被反复使用的概念。临时术语不算。
- **OPI**：一个明确的、可被反驳的主张。一句"今天天气好"不算。
- **CAS**：有主体、动作、结果的具体事例，可核验。
- **SOL**：有适用条件和动作路径的做法。

一段文字同时像多种类型时：按"这段话主要交付什么"判，只归一类，其他用关系表达。

## 常见错误

- 一个文件塞多个单元 → 拆开
- source_documents 只写"自己的旧文章"这种模糊描述 → 必须是能打开的路径
- themes 留空 → 主题地图无法聚合，字段完整性校验会失败
