# 处理流程

## 总原则

1. 原始素材不改写：所有正式处理都发生在新工程里，原目录原文件不碰
2. 对象是内容单元，不是文件：不按文件夹整理，把内容拆成可复用的最小语义对象
3. 结构先于规模：单元口径、关系方向、去重规则没稳定前，不做全量推进
4. 每批结束必须复盘：字段是否改动、关系是否改动、去重是否失控、返工量是否异常

## 标准链路

分类 → 归一化 → 抽取 → 校验 → 登记

1. **分类**：按 来源规则.json 判断素材属于哪类来源；无法分类的先停下问用户，不猜
2. **归一化**：统一放到 `01-原始素材区/完整副本/` 对应目录，不改写内容
3. **抽取**：从文稿中识别 QST/CON/OPI/CAS/SOL 候选，先用工具落草稿，再由 Agent 确认字段
4. **校验**：补齐 themes/keywords/relationships，判重，运行 generate-link-map.js 校验目标
5. **登记**：运行 rebuild-processing-ledger.js 与 summarize-system.js 刷新状态层

## 禁止做法

- 不假装能一次抽全所有语义对象
- 不把每段话都拆成节点（低价值单元比缺单元更伤系统）
- 不在批量阶段改字段规范（要改就停下，按版本规则升级规范，再重跑受影响批次）
- 不用手工批量处理冒充脚本结果

## 每批完成的标准动作

- [ ] 新单元字段完整（summarize-system.js 字段不完整数 = 0）
- [ ] 关系目标缺失 = 0
- [ ] 去重候选已过目并落结论
- [ ] 台账与总览已刷新
- [ ] 复盘记录写入 `03-处理状态/处理状态总览.md` 的"下一步"之上
